## 0. 一句话方案

**以 A 为基座，把它整仓并入 TVBoxApp（保留 936 次上游历史可 rebase），然后做三件事：**

1. **多配置管理**（移植 B 的 `ConfigManager` / `ConfigBean` / `ConfigManageActivity`）——给用户"命名 + 启停 + 主页源"的配置管理能力。

三者按 **Sprint 1 → 2 → 3** 顺序推进，每个 Sprint 独立可交付、独立可回滚。

## 1. 仓库引入策略

### 1.1 为什么用 merge 而不是拷贝

A 的价值有一半在它的 git 历史里（936 commits，能 `git blame` 追到原作者，上游 2026-09 还在更新）。拷贝代码会丢掉这些。

### 1.2 执行步骤

```powershell
cd D:\Study\TVApp\TVBoxApp

# 1) 挂远程
git remote add upstream https://github.com/q215613905/TVBoxOS.git
git remote add local-a  D:\Study\TVApp\TVBoxOS
git remote add ref-b   D:\Study\TVApp\TVBoxOS2

# 2) 取上游完整历史
git fetch upstream --tags

# 3) 合入（两边根提交不同，必须 --allow-unrelated-histories）
git merge --allow-unrelated-histories upstream/main
```

**冲突预判**：两边都有的文件只有 `.gitignore` / `.gitattributes` / `.editorconfig` / `AGENTS.md`。处理原则：

| 文件 | 策略 |
|---|---|
| `.gitignore` | 以 A 为基底，把 TVBoxApp 的签名文件/构建产物规则补进去（A 缺 `*.jks` 忽略） |
| `.gitattributes` | 以 TVBoxApp 为准（它有完整的 `eol=lf` 规则 + linguist 声明，比 A 的完善） |
| `.editorconfig` | 以 TVBoxApp 为准 |
| `AGENTS.md` | 保留 TVBoxApp 版本（路径约束指向本仓库） |

**注意**：A 的 `.gitignore` 里有 `*.md` 一行，会把 `docs/*.md` 全部忽略掉。合并时必须删掉这行，否则本方案的文档进不了仓库。

### 1.3 合并后立即修的三处

```properties
# org.gradle.jvmargs=-Xmx2048m 保持不变
```

| # | 问题 | 处置 |
|---|---|---|

## 3. Sprint 1：多配置管理

### 3.1 目标

用户能保存多条配置地址，给它们起名、单独启停、指定其中一条作为"主页源"，并在设置页一键切换。

### 3.2 为什么 A 需要这个

A 现在的配置管理只有 `HawkConfig.API_URL`（单个字符串）+ `API_HISTORY`（扁平历史数组）+ `API_LINE_LIST`（多仓线路，不是多配置）。缺三样：

1. **多条并存**——换源要重输地址，输错就丢了
2. **命名**——`API_HISTORY` 里全是裸 URL，多到 30 条根本分不清哪个能用
3. **启停 + 主页源**——不能"临时禁用一个源"

### 3.4 与 A 现有机制的接线

**关键设计决策：`ConfigManager` 同步 `HawkConfig.API_URL`。**

B 的 `ConfigManager.syncLegacyApiUrl()` 把第一条启用配置写进 `HawkConfig.API_URL`。这是必须的——A 全仓有 **19 处**代码直接读 `Hawk.get(HawkConfig.API_URL, "")`：

```
api/ApiConfig.java:194        loadConfig 读 API_URL
api/ApiConfig.java:262-264    loadLiveConfig 回退读 API_URL
api/ApiConfig.java:661        switchApiCollectionIfNeeded 写 API_URL
ui/fragment/ModelSettingFragment.java:156  设置页显示
util/HistoryHelper.java       API_HISTORY 维护
```

**结论**：不要重构 A 的 `API_URL` 读取路径，而是**让 `ConfigManager` 成为写入侧的唯一权威**，`API_URL` 退化为"当前生效配置"的镜像。这样改动面最小、回归风险最低。

**接线点**：

| 位置 | 动作 |
|---|---|
| `App.onCreate()` | `ConfigManager.migrateFromLegacy()`——首次启动把老的单 `API_URL` 迁移成一条"默认配置" |
| `ConfigManageActivity` | 新增/编辑/删除/启停/设主页源；每次变更后 `saveConfigs()` → 自动同步 `API_URL` |
| `ModelSettingFragment` | 「配置地址」这一项改为**打开 `ConfigManageActivity`** 而不是直接开 `ApiDialog`；`ApiDialog` 保留给"临时填一个地址试试" |
| `ApiConfig.loadConfig()` | **不动**（它读 `API_URL`，而 `API_URL` 由 `ConfigManager` 同步） |

**切换主页源后的刷新**：`ConfigManageActivity` 里切主页源 → 写 `HawkConfig.API_URL` → 发 `RefreshEvent(TYPE_API_URL_CHANGE)` → `HomeActivity` 重载配置。参照 A 现成的 `RefreshEvent` 机制（`RefreshEvent.java` 已有 `TYPE_API_URL_CHANGE = 8`）。

### 3.5 安全闸（重要）

B 的 `ConfigManageActivity` 里硬编码了三条"内置配置地址"：

```java
private static final String[][] BUILTIN_CONFIGS = {
    {"内置地址A", "http://www.饭太硬.cc/tv"},
    {"内置地址B", "http://xn--z7x900a.net/tv"},
    {"内置地址C", "https://9877.kstore.space/one.json"}
};
```

**这三行不能搬。** 理由见 §7.1：内置具体源地址 = 分发时携带第三方内容，违反"不内置任何具体影视内容"的原则，而且这些域名随时会失效，会给用户"内置的都坏了"的错误印象。

**处置**：删掉 `BUILTIN_CONFIGS` 和 `importBuiltinConfigs()` 的调用入口。用户的配置从哪来？→ **Sprint 2 的自动找源**。两者配合才完整：B 提供管理容器，Sprint 2 提供发现入口。

### 4.4 核心重写：FinderProbe（A 适配版）

这是整个 Sprint 的技术难点。TVApp 的 `SourceProbe` 用的是 TVApp 自己那套 `CmsSite` / `SiteFactory` 抽象，A 里没有这层，而且**A 的站点体系比 TVApp 复杂得多**。

#### A 的站点类型（`bean/SourceBean.java`）

```java
private int type;   // 0 xml 1 json 3 Spider
```

但实际代码里还有 **type 4**（`SourceViewModel.java` 有 `type == 4` 分支，走 `ext` + Base64 参数）。所以 A 实际支持 4 种类型：

| type | 含义 | 请求方式 | 验证可行性 |
|---|---|---|---|
| 0 | XML 采集站 | `GET api?ac=videolist&t={tid}&pg=1` | ✅ 可验证 |
| 1 | JSON 采集站 | `GET api?ac=detail&t={tid}&pg=1` | ✅ 可验证 |
| 3 | jar/js/py 爬虫 | `Spider.homeContent(true)` 等 | ⚠️ **有副作用，见下** |
| 4 | 带 ext 的采集站 | `GET api?ac=detail&filter=true&t={tid}&pg=1&ext={base64}` | ✅ 可验证 |

#### 分层策略

**L1（配置本身能解析）** —— 直接复用 A 的现成逻辑，但要**不污染全局状态**。

A 的 `ApiConfig.parseJson(apiUrl, jsonStr)` 会做一堆全局副作用：`resetConfigData()`（清 spider 缓存、清 `sourceBeanList`）、`setSourceBean()`、写 `HawkConfig.LIVE_GROUP_LIST`……**绝对不能在探针里直接调它**，否则探针会把用户正在用的配置冲掉。

**处置**：写 `ConfigSniffer`，只做只读解析：

```java
public final class ConfigSniffer {
    /** 只读解析：解密 + 提取 sites 列表，不触碰任何全局状态。 */
    public static Sniffed parse(String rawJson, String configKey) { ... }

    public static final class Sniffed {
        List<SourceBean> sites;   // 复用 A 的 bean
        List<Line> lines;         // 多仓 urls[] / storeHouse[]
        boolean encrypted;
    }
}
```

解密复用 A 的 `ApiConfig.FindResult(json, configKey)`——它是 `public static`，且**纯函数无副作用**，可以直接调。

多仓识别复用 A 的 `parseApiCollection` 逻辑（但 A 的那个是 `private`，需要抽出来或重写一份）。TVApp 的 `ConfigLoader.resolveUsable()` 已经实现了"多仓按顺序试线路"，逻辑直接借鉴。

**L2（筛选采集站）** —— 移植 TVApp 的 `SiteFilter.keepCms()`，但判定条件要按 A 的实际类型改：

```java
// TVApp: type == 0 || type == 1
// A:     type == 0 || type == 1 || type == 4   ← 4 也要算，TVApp 那版会误杀
```

**L3（站点真实响应）** —— 按 type 分派，复用 A 的请求构造方式（**不能自己另写一套请求**，A 的站点参数构造有大量细节）：

| type | 验证动作 | 参考 A 的代码 |
|---|---|---|
| 0 / 1 | `GET {api}?ac=videolist\|detail&t={分类id}&pg=1` → 解析出分类列表 | `SourceViewModel.getSort()` / `getList()` 的 type 0/1 分支 |
| 4 | 同上，额外带 `ext`（Base64） | `SourceViewModel.getSort()` 的 type 4 分支 |
| 3 | **不验证**，只计数并标记 | 见 §4.5 |

type 0/1/4 的分类列表解析，A 已有现成的解析器：
- type 1（JSON）→ `AbsSortJson.toAbsSortXml()` → `AbsSortXml.classes.sortList`
- type 0（XML）→ `SourceViewModel.sortXml()`（XStream）

**直接复用 A 的 `AbsSortJson` / `AbsSortXml` / `MovieSort.SortData`**，不要自己写 JSON 解析——A 的 `AbsJsonVod.toXmlVideo()` 处理了 `vod_play_from` / `vod_play_url` 的 `$$$` 分隔符等一堆细节，自己写必踩坑。

**L3.5（能播吗）** —— 可选深挖：取分类第一条 → 详情 → 看有没有播放地址。

```
GET {api}?ac=videolist|detail&ids={id}     ← type 0/1
→ 解析 Movie.Video.urlBean.infoList[].urls 是否非空
```

A 的 `SourceViewModel.getDetail()` 已有这条路径（`params("ids", id)`）。同样只读，不触发 `detailResult` 的 LiveData。

#### 探针的硬约束

| 约束 | 原因 |
|---|---|
| **绝不能调 `ApiConfig.parseJson()`** | 它会 `resetConfigData()` 清掉用户当前配置 |
| **绝不能调 `ApiConfig.loadJar()`** | 会下载并 `DexClassLoader` 加载远程 jar —— 这是**远程代码执行**，探针不能碰 |
| **绝不能调 `ApiConfig.getCSP()`** | 它会走 `jarLoader.getSpider()`，触发 jar 加载（type 3 的 jar 字段） |
| **绝不能调 `ApiConfig.setSourceBean()`** | 会改变首页源 |
| 探针必须用**独立的 OkHttpClient** | 不能复用 A 的 `OkGo`（带 tag 取消机制，`SearchActivity` 会 `cancelTag("search")` 误伤） |
| 探针请求要有独立超时 | A 默认 30s；探针单站 8s 足够，超时要快 |

#### 超时与预算

TVApp 的 `SourceIndex.Probe` 配置：
```json
"probe": { "maxSitesPerConfig": 3, "budgetMs": 25000, "requestTimeoutSeconds": 8 }
```

A 沿用这套，但要说明取舍：
- `maxSitesPerConfig: 3` —— 一个配置里几十个站，全验太慢。验证的目的是判断"这源值不值得保存"，不是给它做体检报告
- `budgetMs: 25000` —— 单个配置的总预算
- `requestTimeoutSeconds: 8` —— 单次请求超时。**A 的 `OkHttp.client()` 默认 30s，必须显式传 timeout**

#### 排序

复用 TVApp 的 `SourceFinder.rank()`（纯函数，可单测）：可用 > 可播放 > 验证通过的站数 > 配置里的站数 > 是否本地。

### 4.5 type 3（jar 爬虫）的处理 ★安全关键

A 的 type 3 站点是 jar/js/py 爬虫。`JarLoader` 用 `DexClassLoader` 加载远程下载的 jar（`JarLoader.java:89`），**本质是执行任意第三方代码**。TVApp 的 `SiteFilter` 直接把 type 3 全部过滤掉，这是对的。

**A 的额外风险**：A 的 jar 加载比 TVApp 更靠前——`ApiConfig.parseJson` 之后马上就会 `loadJar`。自动找源如果导入一个陌生配置，等于**自动执行陌生仓库里的代码**。

**处置（三道闸）**：

1. **探针永不触碰 type 3**。type 3 站点只在 `Finding` 里计数（`siteCount` 里的"非采集站"数），不验证、不加载 jar。
2. **导入需二次确认**。用户在找源页点"使用这个源"时，若配置含 type 3 站点，必须弹窗明示："该配置包含 N 个爬虫站（会下载并运行远程代码），是否继续？"
3. **默认策略可关**。加开关 `HawkConfig.FINDER_ALLOW_SPIDER`（默认 `false`）。关闭时，导入含 type 3 的配置会被直接拒绝。

**但这里有个现实矛盾**：TVBox 生态里，**大量优质源就是 type 3 jar 爬虫**（`csp_JarDemo` 这类）。纯 type 0/1 的配置往往内容很少。

所以最终建议：**默认允许，但在 UI 上明示风险**（符合 A 现在 `TRUST_ALL_CERT` 信任所有证书的既有风格——A 本来就是个"你懂的"应用）。开关留给用户。

### 4.9 定时维护的接线

A 的 `App.onCreate()` 里加一行：

```java
// 自动找源：启动即用本地缓存，后台定时刷新
AutoSourceManager.get(this).start();
```

TVApp 的 `AutoSourceManager` 是 `ScheduledExecutorService` + `Handler(Looper.getMainLooper())`，纯 Java，**A 没有 `WorkManager` 依赖**，直接搬即可。

**A 的额外考虑**：`App.onCreate` 里 `OkGoHelper.init()` 之后才有可用的 OkHttp 客户端。`AutoSourceManager.start()` 必须放在 `OkGoHelper.init()` **之后**，否则探针第一次请求会拿到未初始化的 client。

**调度策略**（TVApp 原样，逻辑正确）：

| 情况 | 下次刷新 |
|---|---|
| 还没缓存 / 从没试过 | 立即 |
| 上次成功 | 1 小时后 |
| 上次失败（GitHub 不通、网络断） | 15 分钟后再试，直到成功 |
| 缓存太旧（>24h） | 立即 |

**"刷新失败绝不覆盖旧缓存"** 是这套设计的关键——否则一次网络抖动就会让 App 变成没有任何源可用。TVApp 的 `persist()` 已经处理对了（只在 `usable` 非空时才 `save`），直接搬。

### 5.1 目标

| B 的文件 | 字节 | 动作 | 适配点 |
|---|---|---|---|

| `util/DownloadManager.java` | 45373 | 搬 + 改 | 见 §5.4 |

B 的 `DownloadManager` 用 `java.net.HttpURLConnection` 而非 OkHttp——**这在 A 上是个问题**，见 §5.4。

### 5.4 关键适配

**(1) 网络层换成 A 的 OkHttp**

B 的 `DownloadManager.openConn()` 用 `HttpURLConnection`，在 A 上会有两个问题：

- **丢掉了 A 的 TLS 兼容层**。A 的 `SSLSocketFactoryCompat` 给 API<21 手工设置 TLS1.2 + cipher 白名单。`HttpURLConnection` 在 4.4 上默认不开 TLS1.2 → **所有 https 下载全挂**
- **拿不到全局代理 / DoH 设置**。A 的 `OkGoHelper` 配了 `ProxySelector` / `ProxyAuthenticator` / DoH DNS

**处置**：改用 `com.github.catvod.net.OkHttp`（它已经带 `SSLSocketFactoryCompat` + `OkDns` DoH）。

**(2) 下载 headers 必须透传**

这是 B 的 `TODO.md` 里第 ① 条踩坑：**"下载要透传播放时的 headers（UA/Referer/Cookie），否则防盗链源 404"**。

A 里播放的 headers 从哪来？`PlayFragment.getHeaders(info)`（`PlayFragment.java:2121` 附近）从解析结果的 JSON 里读 `header` / `referer` / `user-agent`。

**接线**：`DetailActivity` 的缓存按钮 → 先解析出播放地址 + headers → 再入队下载。

**(3) m3u8 下载**

B 的 `TODO.md` 第 ② 条：**"#EXT-X-KEY 做 AES-128 CBC 解密"**。B 的 `DownloadManager.downloadM3u8()` 已经实现了（含 `aesDecrypt` / `rewriteTsTimestamps` / PTS 重写），直接搬。

**(4) 其余 B 已踩过的坑（原样照搬，不要重新发明）**

| # | 坑 | B 的处置 |
|---|---|---|
| ③ | 三合一地址（`真实URL@播放方式@名称@集数`） | 先清掉 `@` 后缀再下载 |
| ④ | m3u8 分片合并输出 `.ts` 而非 `.mp4` | 内容其实是 TS 流，扩展名错了放不出来 |
| ⑤ | 下载完成探测文件头 | HTML / 防盗链页判失败，防假文件 |
| ⑥ | 重启恢复的"下载中"任务无线程永久卡死 | 重启时直接标失败，允许重新入队 |
| ⑦ | 同 URL 失败任务重复堆积 | 重新入队时清理历史失败任务 |
| ⑧ | 净化 m3u8 走 `127.0.0.1:port` | 下载器不能把 127.0.0.1 一律排除 |

**关于 ⑧**：A 的 `M3U8_PURIFY` 也用本地代理（`util/Proxy.java:223`，`ControlManager.get().getAddress(true) + "proxy?go=live&..."`）。所以 A 侧同样有这个问题，照 B 的做法处理。

**(5) 存储位置**

B 的 `getCacheDir(context)`。A 的 `FileUtils` 已有 `getExternalCachePath()` 等工具，对齐 A 的目录约定。

**(6) 权限**

A 的 `AndroidManifest.xml` 已有 `READ_EXTERNAL_STORAGE` / `WRITE_EXTERNAL_STORAGE`。API 29+ 需要 `requestLegacyExternalStorage`，A 的 `targetSdk 28` **天然规避**了这个问题。

## 7. 安全与合规

### 7.1 不内置具体源

**红线**：APK 里**不写死任何具体的第三方影视配置地址或直播地址**。

原因：
- AGPL-3.0 项目分发时的合规负担
- "内置地址"是把第三方内容打包进你的分发物
- 这些域名会失效，用户体验反而更差（"内置的都坏了"）
- 有法律风险

**具体落地**：
- Sprint 1 的 `ConfigManageActivity.BUILTIN_CONFIGS` → 删
- Sprint 2 的 `source_index.json` 的 `sources[]` → 清空
- Sprint 2 的 `default_config.json` → 换成不含真实 api 的示例结构
- Sprint 3 无影响

**替代来源**：全部靠自动找源（用户主动触发）+ 用户手动填写。

### 7.2 jar 爬虫 = 远程代码执行

A 的 `JarLoader`（`JarLoader.java:89`）用 `DexClassLoader` 加载远程下载的 jar。虽有 `;md5;` 校验（`JarLoader.java:157-170`），但**md5 是配置里自带的，配置本身就是不可信的**。

自动找源会**放大**这个风险：自动导入陌生仓库的配置 = 自动引入陌生 jar。

**处置**（详见 §4.5）：
1. 探针永不加载 jar
2. 导入含 type 3 的配置时弹窗明示
3. 提供开关 `FINDER_ALLOW_SPIDER`

### 7.3 `TRUST_ALL_CERT`

A 的 `catvod/net/OkHttp.java` 里的 `TRUST_ALL_CERT` 信任所有证书，`hostnameVerifier` 恒 true。这在老设备（根证书缺失）上是必要妥协，但应做成开关。

**处置**：加 `HawkConfig.STRICT_SSL`（默认 `false` = 保持现状），开启后用系统默认信任链。这项不阻塞主线，可延后。

### 7.4 AGPL-3.0

A 和 B 都是 AGPL-3.0。**个人自用不分发 → 无开源义务。一旦把 APK 给任何人（哪怕朋友），必须同时提供修改后的完整源码。**

本项目所有新增代码按 AGPL-3.0 对待，保留 A 的 LICENSE 文件。

### 7.5 签名

A 的 `.github/workflows/TVBoxOSC.jks` 是公开弱口令 keystore（CI 里明文 `RELEASE_STORE_PASSWORD=TVBoxOSC`）。

**处置**：
- 删除该 jks
- 自建 keystore（密码存 `keystore.properties`，已在 `.gitignore`）
- CI 改用 GitHub Secrets

## 11. 修正记录

对 `选型对比.md` 中的一处事实修正：

**B 的"聚合搜索智能合并"落点写错了。** 原文写 `data/SearchPresenter.java` + `data/DbHelper.java`，实际这两个文件只是 Room 搜索历史的存取（`SearchHistory` 增删查），**与聚合无关**。真正的聚合实现在 `ui/activity/SearchActivity.java`：`mergeIntoAdapter()`（同名视频聚合到同一栏位）+ `relevanceScore()`（拼音首字母相关性排序，`util/PinyinUtil.java` 提供 GB2312 离线拼音）。

这不影响选型结论（该功能仍属 B 独有），但影响移植清单的准确性——要移植的是 `SearchActivity` 的聚合/排序逻辑，不是那两个 data 类。

**另外**：`选型对比.md` §3.2 表格里说 B 用 `com.acsbendi.requestinspectorwebview`（7 处引用），实测 B 仓库里该关键字共 **14 处**命中（含 gradle 声明）。结论不变（该库 minSdk 21，破坏 A 的 API 19 支持），仅计数修正。

### 13.3 与原方案的偏差

| 项 | 原方案 | 实际 | 原因 |
|---|---|---|---|
| 下载管理器包路径 | `util/DownloadManager` | `download/DownloadManager` | A 的 `util/` 已被 `HawkConfig` / `OkGoHelper` 等基础设施占满，下载是独立子系统，单开包更清晰 |
| 本地文件播放 | 复用 B 的 `PlayActivity` | 新写 `LocalPlayActivity` | **A 根本没有独立的播放 Activity**——点播走 `DetailActivity` 内的 `PlayFragment`，直播走 `LivePlayActivity`，B 的 `PlayActivity` 是 B 独有的。移植 B 的话要连 B 的播放器栈一起搬，违反 §6 的"不搬多引擎播放器"。新写的 `LocalPlayActivity` 复用 A 的 `PlayerHelper` + `VideoView`，只 100 行 |
| 缓存总开关 | `HawkConfig.CACHE_ENABLE` | 未加 | B 的开关默认关闭，藏在「播放设置」子页里。A 的设置页结构不同，硬塞进去成本高收益低。缓存是**纯增量功能**（不影响主流程），不设开关反而更省事 |
| 缓存入口 | 详情页按钮 | 详情页按钮 + 用户菜单「缓存」 | A 的用户菜单（`fragment_user.xml`）是 6 宫格，比 B 的侧边栏更好找，追加一项成本低 |
| 删任务时取消下载 | B 里是个空 `if`（注释说"OkHttp取消不保证"） | 给每个任务派生独立 tag，精确取消 | B 的实现确实是个空壳。这里按 `taskId` 派生 tag，删一个任务不会误伤其它在途下载 |
| `BITRATE_TARGET_MAX/MIN` | — | 未搬 | 查证 B 源码：这两个局部变量**声明后从未被引用**（死代码），实际选码率逻辑只用了 `bandwidthPref` |
| 浮动日志窗 | B 的 `FloatLogManager` | 改用 A 的 `LOG` | `FloatLogManager` 是 B 特有的悬浮窗 UI，A 没有对应物；A 的 `LOG` 已同时写 logcat 与文件 |

### 13.4 移植保真度

`DownloadManager` 的核心算法（`readPts` / `writePts` / `readPcr` / `writePcr` /
`rewriteTsTimestamps` / `aesDecrypt` / `isHtmlResponse` / `detectFileType` /
`verifyAndFix` / `downloadM3u8` / `addTask` / `retryTask` / `pauseTask` / `resumeTask` /
`clearAll` / `getTotalSize`）已逐方法与 B 源码做过规范化 diff，**逻辑完全一致**，
差异仅限：import 简写（`java.io.File` → `File`）、日志调用（`FloatLogManager` → `LOG`）、
以及 §13.3 列出的两项实质改进。

> 移植过程中曾因手工转写引入 5 处括号不配对（`readPts` / `readPcr` 各 3~4 处），
> 靠逐方法 diff 抓出并修正。**结论：这类二进制操作和长位运算代码，手抄必错，
> 必须 diff 比对。**
