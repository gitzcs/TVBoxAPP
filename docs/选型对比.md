# 两个 TVBox 开源工程对比与选型结论

> 对比时间：2026-10-21
> 本地副本：A = `D:\Study\TVApp\TVBoxOS`（q215613905/TVBoxOS）
> 　　　　　B = `D:\Study\TVApp\TVBoxOS2`（kkln77620/TVBoxOS）
> 所有数据来自本地仓库源码、git 历史、GitHub API，以及直接从 Google Maven 下载 aar 解出的 `AndroidManifest.xml`（用于确认依赖真实 minSdk）。

---

## 1. 结论先行

**以 A（q215613905/TVBoxOS）为基座二次开发，把 B 当"功能清单 + 参考实现"来移植，不重新造轮子。**

决定性理由只有一条：**Android 4.4（API 19）是你的硬约束，A 原生满足，B 结构性排除。**

```
A: app 的 java / java32 / python / python32 四个 flavor → minSdkVersion 19
   player / quickjs / pyramid 三个子模块            → minSdkVersion 19
   还自带 API<21 的 TLS1.2 兼容层 + XWalk WebView 兜底

B: app 的 normal / python flavor → minSdkVersion 21
   quickjs / pyramid            → minSdkVersion 21
   appcompat 1.7.0（实测 minSdk=21）
   → 想支持 4.4 需要"逆向降级"，且无人维护兜底
```

其余五条理由都是加分项，见 §4。

> ⑦ 同 URL 的失败任务重新入队时要先清历史；
> ⑧ 走本地净化代理的 m3u8 是 `127.0.0.1:port`，下载器不能把 127.0.0.1 一律排除。

## 6. 安全与合规

1. **两个项目都是 AGPL-3.0。** 个人自用不分发 → 没有开源义务；**一旦把 APK 给任何人（哪怕朋友）**，就必须同时提供你修改后的完整源码，且保持 AGPL-3.0。方案里所有新增代码也要按 AGPL-3.0 对待。
2. **A 的仓库里内置了签名文件** `.github/workflows/TVBoxOSC.jks`，且 CI 里明文写着 `RELEASE_STORE_PASSWORD=TVBoxOSC` / `RELEASE_KEY_PASSWORD=TVBoxOSC`。**这是公开的弱口令 keystore，二开必须换成自己的**，否则别人能签出"你"的升级包。
3. **jar 爬虫 = 远程代码执行。** A 的 `JarLoader` 用 `DexClassLoader` 直接加载远程下载的 jar，虽有 `;md5;` 校验，但本质是执行任意第三方代码。我们要做的"自动找源"会**放大**这个风险（自动导入陌生仓库的配置 = 自动引入陌生 jar）。因此自动找源方案里必须有一道闸，见 [实现方案 §6](实现方案.md)。
4. `TRUST_ALL_CERT`（信任所有证书）在 A 里是默认行为。对老设备缺根证书是必要的妥协，但建议做成开关，并在 UI 上明示。
5. B 的 README 也写了「仅供学习交流使用，请勿用于商业用途」。自动找源只做"发现 + 探测 + 展示 + 本地保存"，**不要在包里内置任何具体影视内容或写死的第三方配置地址**（内置索引里只放"去哪里找"的规则，不放具体源），由用户自行决定是否导入。

## 7. 为什么不"基于两个重新开发"

你本地其实已经有一个从零自研的工程 `D:\Study\TVApp\TVApp`（`com.video.tvapp`，AGP 8.6.0 / Gradle 8.14.3 / minSdk 19 / 纯 Java + 脱糖，6 个模块 net·config·spider-api·data·player·app，约 19,000 行，42 次提交，已产出 13.97MB debug APK）。它的架构很干净，`config/finder` 包里**自动找源 + 三层验证 + 本地缓存 + 定时重试已经全部实现**，文档也写得很好。

但它的现状是：Sprint 4/5/6 之后**只写了代码，没经过完整构建和真机验证**，且 V1 明确把 jar 爬虫（type 3）、解析嗅探、EPG、聚合搜索页、DLNA、弹幕全部推到了 V2+。也就是说，要从 TVApp 走到"能日常用的电视影视 App"，还得补齐 TVBox 生态里最难的那几块（jar 爬虫反射加载、WebView 嗅探、直播 EPG）。

所以三条路的成本对比是：

| 路线 | 到"可用"的代价 | 长期维护 |
|---|---|---|
| 基于 A 二开 | **低**。A 已经是完整可用产品（直播/弹幕/字幕/投屏/jar爬虫/嗅探全有），只需加"自动找源"和移植 B 的多配置管理 | **好**。上游活跃，可持续 rebase |
| 基于 B 二开 | 中高。要先做 minSdk 降级 + 修 Windows 构建 + 换 JDK 17 | **差**。已停更，无上游可 rebase |
| 继续 TVApp 从零 | **高**。要自己实现 jar 爬虫 / 嗅探 / EPG，这些是 TVBox 生态里最耗时且最容易踩坑的部分 | 好（完全自主），但代价是自己扛全部生态适配 |

**推荐：基于 A 二开，把 TVApp 当设计蓝本和零件库。** TVApp 的 `config/finder` 七个类（`Finding` / `SourceIndex` / `RepoScanner` / `SourceProbe` / `SourceFinder` / `SourceCache` / `AutoSourceManager`，共约 2,241 行，带 JUnit 测试）可以**几乎直接移植**到 A —— 它不依赖 TVApp 的 UI，只依赖 `net` / `config` / `spider-api` 三个模块的接口，把这些接口映射到 A 的 `OkHttp` / `ApiConfig` / `SourceViewModel` 即可。这等于省掉自动找源功能的全部设计与踩坑成本。

## 10. 具体怎么把 A 引进 TVBoxApp（保留可 rebase 的历史）

`TVBoxApp` 目前是空仓（2 个 init 提交，只有 AGENTS.md / .editorconfig / .gitattributes / .gitignore / .gitmessage）。推荐做法：

```powershell
cd D:\Study\TVApp\TVBoxApp

# 1) 把 A 的两个远程都挂上：upstream 用于跟官方，local 便于对照
git remote add upstream https://github.com/q215613905/TVBoxOS.git
git remote add local-a  D:\Study\TVApp\TVBoxOS
git fetch upstream --tags

# 2) 合入 A 的完整历史（--allow-unrelated-histories 因为两边根提交不同）
git merge --allow-unrelated-histories upstream/main
#    冲突只会出现在 .gitignore / .gitattributes / .editorconfig 这类双方都有的文件，手工合并即可

# 3) 之后要跟进上游（A 的活跃开发在 dev 分支）
git fetch upstream
git log --oneline HEAD..upstream/dev     # 看上游新增了什么
git merge upstream/dev                   # 或 cherry-pick 单个提交
```

这样做的好处：`git log` 里能看到 A 全部 936 次提交，`git blame` 能追到原作者，上游更新可以持续 merge。相比"拷一份代码进来"，长期维护成本低一个量级。

同时把 B 挂成只读参照，方便移植时对照：

```powershell
git remote add ref-b D:\Study\TVApp\TVBoxOS2
git fetch ref-b --no-tags
# 之后可以用 git show ref-b/main:app/src/main/java/com/github/tvbox/osc/util/DownloadManager.java 直接看 B 的实现
```
